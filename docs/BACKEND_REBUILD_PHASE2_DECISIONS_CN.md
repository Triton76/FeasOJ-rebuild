## 2. 总体原则

1. 采用破坏性重构，不以兼容旧服务为目标。
2. 仅继承此前项目中可复用的能力形态，不继承旧实现代码。
3. API 采用 clean break，新接口语义优先。
4. 当前阶段以课程设计目标为准，不要求生产级迁移与回滚方案。

## 3. 第二阶段已拍板决议

### 3.1 鉴权与身份
1. 仅使用短期 access token。
2. access token TTL 为 2 小时。
3. 不引入 refresh token。
4. 写操作身份仅从 JWT claims 获取，不信任请求体 user_id。

### 3.2 账号与邮件
1. 教师账号由管理员创建。
2. 教师初始密码由管理员手动输入。
3. 暂不实现忘记密码流程。
4. 邮件能力落地 SMTP 真实发送。
5. SMTP 发送失败不重试，直接返回错误。
6. 当前仅按 dev 模式推进，不区分环境初始化分支。

### 3.3 权限与班级
1. teacher 仅可见本人 private 资源。
2. class 资源仅限所属班级范围。
3. 班级申请采用永不过期、人工处理。
4. 后台提供待处理列表，按创建时间倒序展示。

### 3.4 提交与判题链路
1. 判题采用异步队列模式。
2. 队列语义为至少一次投递。
3. 以 submission_id 作为幂等键。
4. judge 回传采用内网信任模式。
5. judge 回传不额外增加来源 IP 白名单。

### 3.5 竞赛与榜单
1. 竞赛密码风控不做锁定，仅记录日志。
2. 竞赛密码风控不增加最小限流。
3. 榜单口径按 ACM 赛制执行。

### 3.6 范围与工程化
1. 第二阶段不实现搜索能力。
2. 可观测性基线为 JSON 日志 + 基础指标。
3. 质量门槛为关键 usecase 单测 + 认证/提交流程集成测试。
4. 发布切换不做回滚预案。

## 5. 实施约束

1. 不因为兼容旧接口而引入长期历史包袱。
2. 不在第二阶段扩展未拍板能力（如搜索、refresh token、复杂回滚）。
3. 若新增决议，必须先补充本文再进入实现。

## 7. 开工前 P0 对齐（已拍板）

> 目的：在进入第二阶段里程碑开发前，先完成最小且必要的契约收敛，避免边开发边返工。

### 7.1 范围级别
1. 采用“标准 P0”范围。
2. 标准 P0 包含：
	- 鉴权与身份契约收敛（TTL、身份来源、重置密码下线）。
	- M3 判题链路的队列端口抽象与本地内存实现骨架。
	- 基础质量门槛测试补齐（见 7.6）。

### 7.2 鉴权与账号对齐
1. access token TTL 固定为 2 小时。
2. 不引入 refresh token。
3. 完全下线重置密码相关接口与契约（不保留对外可调用入口）。

### 7.3 写操作身份策略
1. 写操作身份仅来自 JWT claims。
2. 请求体中的 user_id 相关输入不作为身份依据。
3. 服务端统一以 claims 用户身份覆盖写入主体。

### 7.4 M3 判题链路先行落地策略
1. 先定义队列 Port 抽象，再提供本地内存实现用于语义验证。
2. 队列语义按“至少一次投递”实现。
3. 以 submission_id 作为幂等键，先落去重语义与处理流程。
4. 后续可在不改业务层语义的前提下替换为真实 MQ 实现。

### 7.5 本阶段不做事项（重申）
1. 不扩展搜索能力。
2. 不引入 refresh token。
3. 不引入复杂回滚与迁移预案。

### 7.6 开工前质量门槛（基础档）
1. 补齐 Auth 关键 usecase 单测。
2. 补齐 SubmitRecords 关键 usecase 单测。
3. 补齐 1 条认证与提交流程集成测试主链路。

### 7.7 执行顺序
1. 先做鉴权契约收敛（TTL、重置密码、身份来源）。
2. 再做 M3 队列端口抽象与本地实现骨架。
3. 最后补齐基础档测试并作为开工门槛验收。
